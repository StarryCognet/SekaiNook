### 已确认的口径（这些是拍过板的，别再改）

| 需求 | 拍板口径 | 理由 |
|---|---|---|
| ① 默认 100 | 新账号一次性「开户礼金」+100，靠固定 id `seed_welcome_bonus` 保证只发一次；判定条件是「既无 seed 记录、也无任何真实用户流水」，**老账号不会凭空多 100** | 直接加余额会让老账号也 +100 |
| ② 每日 <5 扣 10 | **只对「确实已经过完的那一天」判罚款**：晚上 22:00 之后打开 → 结算今天；否则 → 结算昨天。一天只扣一次 | 按字面「当日不足 5 个就扣」的话，早上首次打开时今天必然还没流水（完成数恒为 0）⇒ 等于每天都无条件扣 10，把需求做反了。此语义已与用户确认（选项 C） |
| ③ 余额改积分 | 只改**算钱口径**的单位：「阳光」→「积分」；**栏目名保留**（阳光花园 / 阳光商城） | 用户选了「只统一算钱单位、保留栏目名」 |

## 4. ⚠️ 关键约束：本项目**没有线上 migration 执行通道**

`functions/` 下只有 `api/`（images / ledger / maintenance / notifications / plans / settings / upload），
**没有 `scheduled` handler**。

推论（决定了整个设计）：
- 「每天不足 5 个扣 10」「22:00 没打卡睡觉扣 20」**不可能半夜自动跑**，只能在**下次打开页面时补记** ⇒ 这就是 `settle.ts` 存在的原因，也是它必须「幂等靠固定 id + 回填 created_at 到正午」的原因。
- **本次改动不需要任何 DDL**：没有新表、没有新列，全部复用 `family_ledger` 既有列（`id/task_id/task_name/type/amount/note/image_url/status/created_at/member`）⇒ **用户不需要手动跑 SQL**。
- 新增的规则（`custom:*`、`user_task_exec`、`seed_welcome_bonus`、`daily_min_tasks_penalty`）都只是**代码里的常量**，随部署生效。

# 小米运动健康（Mi Fitness）官方数据接入方案

> 面向 SekaiNook（React + Cloudflare Pages Functions + D1 + R2）的落地方案
> 调研日期：2026（文档版本号见各来源链接的「更新时间」）
> 全部结论来自小米澎湃OS开发者平台官方文档，非二手转述

---

## 0. 一句话结论

**有官方 API，但只有两条路，且都要求先过小米的资质审核：**

| 路径 | 形态 | 适用 SekaiNook？ | 硬门槛 |
|---|---|---|---|
| **服务端接入（云对云）** | HTTPS REST + OAuth2 | ✅ **推荐**，与 Cloudflare 架构天然契合 | 企业资质审核 + 上线要交 APK/演示视频 |
| 客户端接入（端侧 SDK） | Android AIDL SDK | ❌ 不适配（Web 应用） | 仅小米手机 + HyperOS 4.0+ + 仅中国大陆 |
| ~~小米健康云 Android SDK~~ | 旧版 SDK | ❌ 已关闭 | 官方原文：「只对小米生态链企业及合作伙伴正式开放」 |

**最大的现实风险不在技术，在准入**：服务入口目前是**灰度开放**（原文：「本功能尚未全量上线，未开放的账号无法看到功能入口」），且资质表单要求填**官网链接、隐私政策链接、用户协议链接**，上线还要提交 **APK + 合规演示视频 + 自检清单 + 举证材料**。个人开发者/家庭自用工具通过概率低。

→ 因此本文档给出 **A 方案（官方，正式产品走这条）** 和 **B 方案（轻量替代，先跑通业务闭环）**，可并行推进。

### 1.1 申请与上线全流程（pId=2326）

1. 登录 [小米澎湃OS开发者平台](https://dev.mi.com/xiaomihyperos/home) → 管理中心 → 选择应用
2. 左侧【开发】→【开放服务】→ 找到「小米运动健康」→【启用服务】
3. **签署协议**
4. **填写资质信息**：联系人姓名/联系方式、接入功能描述（200字内）、**申请资料清单（须下载官方 Excel 模板填写后上传）**、隐私政策链接、用户协议链接、官网链接（均须 `https://` 开头）
5. **选择数据权限** + 填回调地址（`https://` 开头，用于订阅推送）→ 提交审核
6. **审核 2-5 个工作日**，不通过可按驳回理由重新提交
7. **配置签名证书指纹**（测试/正式各至少 1 个，最多 5 个）
8. 开通后进【开发测试】，可加最多 **20 个测试账号**白名单
9. **发布上线**：上传合规性演示视频（mp4，<1G，须包含 OAuth 授权全过程 + 每个权限的用途演示）、自检清单 Excel、举证材料 Zip、**APK 包**
10. 上线审核通过后权限才在正式环境生效

> 关键含义：**第 9 步要 APK**。这意味着纯 Web 应用在「发布上线」环节可能被卡。建议提前向平台客服（developer@xiaomi.com）确认 Web 应用是否可作为接入主体。

## 2. A 方案：服务端接入（云对云）技术全解

### 2.1 服务地址与公共请求头

- **数据平台域名**：`https://hlthopen.io.mi.com/`
- **账号服务**：`https://account.xiaomi.com/`

所有数据接口公共 Header（pId=2333「公共参数说明」）：

| Header | 必填 | 值 |
|---|---|---|
| `Content-Type` | ✅ | `application/json` |
| `Authorization` | ✅ | `Bearer ${access_token}` |
| `X-Client-ID` | ✅ | 开放平台分配的应用标识 |
| `X-Client-Nonce` | ✅ | 12 字节 → base64url，**不可重复**（见 §2.4） |
| `X-Trace-Id` | 否 | 建议携带，用于链路追踪 |

### 2.2 OAuth2 授权码模式三步

**Step 1 — 拉起授权页（GET）**

```
https://account.xiaomi.com/oauth2/authorize
  ?client_id=<应用ID>
  &redirect_uri=<回调地址，须与申请时一致>
  &response_type=code
  &scope_provider=healthkit          ← 必须是 healthkit
  &state=<随机串，防 CSRF，强烈建议传>
  &skip_confirm=false                ← false = 每次都展示授权页
```

- `scope` 可选：不传则采用该应用已获批的全部权限；传则多个用空格分隔（传 scope_id，如 `200016 200009`）
- 授权成功后重定向：`http://example.com/example?code=CODE&state=STATE`
- **code 有效期 10 分钟，且只能用一次**

**Step 2 — 换 access_token（POST form-urlencoded）**

```
POST https://account.xiaomi.com/oauth2/token
Content-Type: application/x-www-form-urlencoded

code=<授权码>&client_id=<ID>&redirect_uri=<同前>
&client_secret=<AppSecret>&grant_type=authorization_code
```

返回：`access_token`、`expires_in`、`refresh_token`、`scope`、`openId`、`union_id`、`mac_key`、`mac_algorithm`

> ⚠️ **坑**：返回值前面带 `&&&START&&&` 前缀，**必须剥掉再 JSON.parse**。

**Step 3 — 刷新 token**

```
POST https://account.xiaomi.com/oauth2/refresh/token
Content-Type: application/x-www-form-urlencoded

pt=0&client_id=<ID>&redirect_uri=<同前>&client_secret=<AppSecret>
&grant_type=refresh_token&refresh_token=<RT>
```

- `expires_in` 默认 **2 小时**
- 限流：单 client_id ≤ 5000 次/s，超限返回 **HTTP 503**
- 响应里的 `refresh_token` 是**更新后的新 RT，要覆盖存**

**取消授权**（解除绑定）：

```
POST http://open.account.xiaomi.com/user/unbindOAuth2Grained
     access_token=<>&client_id=<>&client_secret=<>
```
判断成功唯一标志 `code=0`。
用户也可自助解绑：**小米运动健康 App > 我的 > 三方数据管理 > 选中应用 > 取消授权**。

**阅读要点**：
- 大部分接口的响应是 `dataPoints[]` / `group[].dataSet[]` 嵌套结构，`value[]` 里按 `fieldName` 区分字段，数值字段是 `integerValue` / `floatValue` / `longValue` / `stringValue` / `mapValue` 五选一。
- 分页统一用 `cursor` + `hasMore`：首次不传 cursor，`hasMore=true` 就带着返回的 cursor 继续，直到 `hasMore=false`。
- 请求示例里出现 `userId` / `clientId` 查询参数，但鉴权靠 `Authorization` + `X-Client-ID`。

### 2.4 X-Client-Nonce 生成（12 字节，大端）

规则（原文）：
- 前 4 byte = uint32 随机数，**大端**
- 中间 4 byte = uint32 随机数，**大端**
- 末 4 byte = **unix 时间戳 / 60**（分钟数）取整，**大端**
- 12 字节整体做 base64 url safe

```ts
// functions/_lib/miHealth/nonce.ts
export function createClientNonce(): string {
  const bytes = new Uint8Array(12);
  const view = new DataView(bytes.buffer);
  const rand = crypto.getRandomValues(new Uint32Array(2));
  view.setUint32(0, rand[0], false);                              // 大端
  view.setUint32(4, rand[1], false);                              // 大端
  view.setUint32(8, Math.floor(Date.now() / 60_000), false);      // 大端
  let bin = '';
  for (const b of bytes) bin += String.fromCharCode(b);
  return btoa(bin).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}
```

### 2.5 订阅推送（替代轮询的关键能力）

官方第一句就是「**优先使用时间窗口、分页 cursor 和订阅通知能力，避免高频全量轮询**」。

- 注册：`POST /healthkit/subscribe/change`，body `{ eventTypes: [{eventType, subType}], userId, clientId }`
- 回调：小米 `POST https://<你的回调地址>/healthkit/notifications`
- **验签**：Header `x-notification-signature` = `HMAC-SHA256(openId_eventType_subType_eventTime, AppSecret)` 的**十六进制小写**
- body：`{ openId, eventTime, eventType, subType, metaData[{metaKey,metaValue}] }`
- **必须返回 HTTP 200**，否则视为失败

可用事件：

| eventType | subType | metaData 关键字段 |
|---|---|---|
| `USER_EVENT` | `CANCEL_ALL` / `CHANGE_SCOPE` | — |
| `FITNESS_DATA_EVENT` | `UPDATE` | startTime / endTime / dataType / timeZone / recordDay |
| `FITNESS_AGGREGATED_DATA_EVENT` | `UPDATE` | 同上 |
| `FITNESS_RECORD_DATA_EVENT` | `UPDATE` | datatype（睡眠记录走这里） |
| `SPORT_RECORD_DATA_EVENT` | `UPDATE` | sportKey |

支持订阅的数据类型：体重、心率、血氧、最大摄氧量、步数、卡路里、中高强度、步数总量、卡路里总量、中高强度统计、活力指标、睡眠记录、心率过速/过缓、运动记录。
（有效站立、心率统计、血氧统计、最大摄氧量统计**不支持**订阅；专业运动数据也不支持。）

验签实现：

```ts
// functions/_lib/miHealth/verify.ts
export async function verifyNotification(
  openId: string, eventType: string, subType: string, eventTime: string,
  received: string, secret: string,
): Promise<boolean> {
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(secret),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'],
  );
  const mac = await crypto.subtle.sign(
    'HMAC', key, new TextEncoder().encode(`${openId}_${eventType}_${subType}_${eventTime}`),
  );
  const expected = [...new Uint8Array(mac)].map((b) => b.toString(16).padStart(2, '0')).join('');
  if (expected.length !== received.length) return false;
  let diff = 0;
  for (let i = 0; i < expected.length; i += 1) diff |= expected.charCodeAt(i) ^ received.charCodeAt(i);
  return diff === 0;   // 定长比较，避免时序侧信道
}
```

## 3. 与 SekaiNook 的集成架构

### 3.1 为什么服务端接入和这个项目天然契合

| 官方要求 | SekaiNook 现状 |
|---|---|
| 需要服务端存 `client_secret` | ✅ Cloudflare Pages 环境变量（加密） |
| 回调地址必须 `https://` | ✅ Pages 默认 https |
| 需要服务端发起 OAuth code→token | ✅ `functions/api/**` Node/Workers runtime |
| 需要稳定存 refresh_token / 增量数据 | ✅ D1 |
| 需要高频读缓存给前端图表 | ✅ D1 本地读，不反复打小米接口 |
| 需要一个公网可访问的 HTTPS 推送端点 | ✅ `functions/api/mi-health/notify.ts` |

**不需要**新引入任何依赖，不违反 `@SPEC.md` 的技术栈。

### 3.2 建议的业务闭环（数据用来做什么）

SekaiNook 现有规则里有几条可以**由小米数据自动判定**，这是最有价值的切入点：

| 现有任务 | `config/familyRules.ts` | 可否自动化 |
|---|---|---|
| 按时睡觉 +10（19:00-22:00 打卡） | `sleep_on_time` | ✅ 用 `com.xiaomi.sleep.health` 的入睡时间 |
| 未按时作息 -20 | `sleep_penalty` | ✅ 同上，超时自动扣分 |
| 课外阅读 30 分钟 +10 | `read_book` | ❌ 无法自动判定 |
| （建议新增）每日步数达标 | 新任务 | ✅ `com.xiaomi.steps.total` |
| （建议新增）每日运动打卡 | 新任务 | ✅ `/healthkit/sportRecords/all` |

推荐第一期只做**睡眠自动判定**（数据稳定、覆盖每晚、家长最关心），跑通后再加步数/运动。

`client.ts` 骨架（注意：**所有错误都要归一化，不抛原始响应**）：

```ts
// functions/_lib/miHealth/client.ts
export interface MiHealthEnv {
  MI_HEALTH_CLIENT_ID: string;
  MI_HEALTH_CLIENT_SECRET: string;
}

const BASE = 'https://hlthopen.io.mi.com';
const TOKEN_URL = 'https://account.xiaomi.com/oauth2/token';
const REFRESH_URL = 'https://account.xiaomi.com/oauth2/refresh/token';

/** 小米 token 接口会在 JSON 前带 &&&START&&& 前缀 */
function stripPrefix(text: string): string {
  return text.startsWith('&&&START&&&') ? text.slice('&&&START&&&'.length) : text;
}

export async function miFetch(
  env: MiHealthEnv, path: string, accessToken: string, params: Record<string, string>,
): Promise<unknown> {
  const url = new URL(path, BASE);
  for (const [k, v] of Object.entries(params)) url.searchParams.set(k, v);
  const res = await fetch(url.toString(), {
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${accessToken}`,
      'X-Client-ID': env.MI_HEALTH_CLIENT_ID,
      'X-Client-Nonce': createClientNonce(),
    },
  });
  const text = await res.text();
  if (!res.ok) throw new MiHealthError(res.status, text.slice(0, 500));
  return JSON.parse(text) as unknown;
}

export async function exchangeCode(
  env: MiHealthEnv, code: string, redirectUri: string,
): Promise<MiTokenResponse> {
  const body = new URLSearchParams({
    code, client_id: env.MI_HEALTH_CLIENT_ID, redirect_uri: redirectUri,
    client_secret: env.MI_HEALTH_CLIENT_SECRET, grant_type: 'authorization_code',
  });
  const res = await fetch(TOKEN_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: body.toString(),
  });
  return JSON.parse(stripPrefix(await res.text())) as MiTokenResponse;
}
```

### 3.6 定时同步怎么办（重要限制）

**Cloudflare Pages 没有内建定时器机制**（Pages Functions 不提供 scheduled handler；社区多次踩坑记录）。三种解法，按推荐度：

1. **优先用订阅推送**（§2.5）——数据变化时小米主动 POST 到 `/api/mi-health/notify`，无需定时器。这是官方推荐的姿势，也最省配额。
2. **进页面增量补齐**——前端打开工作台时调 `/api/mi-health/sync`，按 D1 里记录的最后 `record_day` 往前补 1~7 天（注意 `aggregate/dailies` 窗口 ≤7 天）。
3. **兜底：一个独立的小 Worker 配 Cron Triggers**，绑定同一个 D1 做夜间补数。这会新增一个部署单元，需要先确认是否接受。

## 4. 必须提前确认的风险与红线

### 4.1 准入（最大风险）

- 服务入口灰度开放，**未开放账号看不到入口** → 先登录开发者平台确认入口是否可见
- 资质要企业/应用级别的官网、隐私政策、用户协议
- 发布上线要 **APK**，纯 Web 应用可能被卡 → 建议先发邮件问 developer@xiaomi.com
- 个人开发者身份能否过审未知，文档未明确禁止，但要求明显偏企业

### 4.2 合规（健康数据 = 敏感个人信息）

孩子的心率/睡眠/血氧属于《个人信息保护法》下的**敏感个人信息**，需要：
- 单独同意 + 告知必要性与影响
- 必须有隐私政策说明收集范围、用途、保存期限、共享情况
- 必须有撤回授权通道（小米侧 App 内已自带，产品内也应提供）

> **建议**：第一期只接「睡眠时段」和「步数」，不接心率/血氧/位置，把合规面压到最小。位置数据（`com.xiaomi.location.sample`）尤其不建议接。

### 4.3 架构冲突（必须改 SPEC）

`@SPEC.md` 第 51 行铁律：

> 接口默认不鉴权（不引入鉴权中间件/共享口令校验）：家庭内部工具，权限由前端身份 + 家长口令承担，后端接口保持公开。

**这条必须改**。一旦后端存了 `refresh_token`、并能拉到某个孩子的心率睡眠数据：
- `/api/mi-health/summary?member=kid` 不能是公开接口
- `/api/mi-health/notify` 必须验小米签名（已设计）
- `/api/mi-health/authorize` 的 `member` 参数不能由调用方随意指定

**最小改造包**：
1. 引入一条「家长口令 → 会话 Cookie（HttpOnly + Secure + SameSite=Lax）」的路径，仅保护 `/api/mi-health/*`
2. 在 `@SPEC.md` 里把该例外写清楚，避免后续被误认为违反规范
3. `mi_health_binding` 与 `family_ledger.member` 的关联要做归属校验

### 4.4 其他技术坑

| 坑 | 说明 |
|---|---|
| `&&&START&&&` 前缀 | token 接口返回带前缀，不剥会 JSON.parse 失败 |
| RT 会轮换 | refresh 响应里的 `refresh_token` 是新值，必须覆盖 |
| AT 只有 2 小时 | 每次调用前检查 `access_expires_at`，过期就刷 |
| 刷新限流 | 单 client_id ≤5000 次/s，超限 503，要有退避 |
| 历史数据默认不返回 | 不勾「历史数据」权限，只能拿到授权后的数据 |
| 时间窗口 | 采样 ≤30 天；日聚合 ≤7 天；运动记录按 ≤5 天保守实现 |
| 数据延迟 | 血氧等为「小时级」；用户关掉云同步开关时，本地写入不会上云 |
| 解绑要处理 | 收到 `USER_EVENT/CANCEL_ALL` 必须清本地 token 并停止拉取 |
| 回调必须 200 | 推送处理超时要快速返回，重活丢给后续同步 |

## 5.1 非官方私有云 API 路线（HealthMi / mi-fitness-mcp-cn 实证）

> 补充调研：[ShawnDiego/HealthMi](https://github.com/ShawnDiego/HealthMi) 是一个把小米运动健康云端数据写入 Apple Health 的 iOS App（Swift，Apache-2.0）。它**本身不能给 SekaiNook 用**（无服务端、无 API、方向相反），但它实证了一条**完全不需要小米审批**的取数路径，并给出了完整协议。

### 5.1.1 已逆向验证的私有接口

内置参考实现 [mi-fitness-mcp-cn](https://github.com/kubulashvili/mi-fitness-mcp)（MIT，Python，本地 SQLite 缓存 + MCP Server）给出了协议全貌：

1. 登录：用小米账号 `userId` + `passToken`（`account.xiaomi.com` 的 Cookie）经 `serviceLogin` 换取 `ssecurity` 与会话 Cookie
2. 签名：每个请求用 `signed_nonce = SHA256(ssecurity || nonce)` 做 **RC4 加密 + SHA1 签名**
3. 取数接口：
   - `POST https://hlth.io.mi.com/app/v1/data/get_fitness_data_by_time`
   - `POST https://hlth.io.mi.com/app/v1/data/get_sport_records_by_time`
4. 已验证的 `key`：`steps`、`calories`、`heart_rate`、`weight`、`sleep`、`resting_heart_rate`、`spo2`、`stress`、`abnormal_heart_beat`
5. 运动记录响应含 `sport_records` / `has_more` / `next_key`；每条记录的 `value` 是 JSON 字符串，含 `start_time` / `end_time` / `duration` / `distance` / `calories` / `avg_hrm` / `max_hrm`

**重要区分**：私有接口域名是 `hlth.io.mi.com`，官方开放平台是 `hlthopen.io.mi.com` —— 只差几个字母，勿混淆。前者不在开放平台上，因此**无需任何审批**。

**好消息**：私有接口比官方那套 DataSet / DataPoint / HealthRecord / subData 嵌套模型**好用得多** —— 直接 `key=sleep` 就拿数据。

### 5.1.2 四条路线排序（在 A/B 方案之外的补充）

| # | 路径 | 做法 | 评价 |
|---|---|---|---|
| **1** | **本机桥 ⭐** | 家里常开 PC/NAS 跑 `mi-fitness-mcp-cn`（现成 MIT 代码）+ cron，凭据只留在本机；同步后 POST 到 SekaiNook 的 `/api/mi-health/ingest` | **最优**：零审批、凭据不出家门、住宅 IP 与手机风控画像一致、有现成代码可复用 |
| **2** | **手机桥** | 小米云 → HealthMi → Apple 健康 → Health Webhook / HealthRelay / 快捷指令 → POST 到 ingest | 全自动、无需常开电脑；**但必须有 iPhone**，且要串三个 App |
| **3** | 手动录入 | 见 §5 表格 | 今天就能上，兜底 |
| **4** | 官方 API | 见 §2 | 长期正规，短期过审难 |
| **5** | ⚠️ 直接在 Cloudflare Worker 跑私有 API | 把 `passToken` 存 Cloudflare 环境变量 | **不推荐**，理由见 5.1.3 |

### 5.1.3 为什么不在 Cloudflare Worker 里直接跑私有 API

- **`passToken` 约等于账号密码**：HealthMi 特意只存本地 iOS Keychain、绝不上传；放进 Cloudflare 环境变量等于交出小米账号钥匙，且比官方 OAuth 差得多（OAuth 下永远看不到密码）
- **有效期极短**：官方 README 明确写过期后报 `code=70016`，需重新登录复制新 token → 家庭工具会频繁要求手动换 token
- **风控**：从 Cloudflare 数据中心 IP 用 RC4 签名登录 `account.xiaomi.com`，与从本人手机登录的画像差异极大，易触发二次验证甚至封号
- **Web Crypto 不支持 RC4**：移植到 Workers 需手写 RC4（约 30 行），增加维护面
- 违反小米服务条款，接口随时变更，README 自述「接口随时可能变更或失效」

**本机桥（路径 1）恰好规避以上全部问题**：同样的私有接口、同样的凭据，但跑在住宅 IP 的电脑上 —— 与小米手机同一网络环境；Cloudflare 侧只接收规整后的睡眠/步数，看不到任何账号凭据。

### 5.1.4 本机桥的接口设计

新增一个**只接受共享密钥**的窄接口（不必引入完整会话体系）：

```
POST /api/mi-health/ingest
Header: X-Ingest-Secret: <Pages 环境变量 MI_INGEST_SECRET>
Body: { member, record_day, sleep_onset, sleep_total, steps, ... }
```

本机脚本侧用 `mi-fitness-mcp-cn` 同步到本地 SQLite 后，读 `sleep_sessions` / `daily_activity` 表，映射成上面的 body POST 过来。这样：
- `@SPEC.md:51`「接口默认不鉴权」只需一个窄例外（共享密钥），不必引入 Cookie 会话
- `passToken` 永不进入 Cloudflare

### 5.1.5 成熟度提醒

HealthMi 创建于 2026-08-14、最后一次推代码 2026-08-16（仅两天活跃），单作者，22 星 / 8 fork，2 个 open issue —— 项目很年轻。但其工程质量尚可（用 Python 参考实现作"预言机"生成加密测试向量，保证 RC4/签名逐字节一致）。走路径 1 时，**只依赖它验证过的协议，不依赖该 App 本身**。

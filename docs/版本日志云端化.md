# 版本日志云端化（D1 `changelog` 表）

> 一句话：版本日志从「网页版和 App 各存一份代码常量」改成「D1 里一份、两端都读」，
> 加一条日志只需要改一处、同步一次，两边同时可见。

## 为什么改

网页版（`SekaiNook`）和 Flutter 版（`SekaiNook-App`）是两个仓库、各自打包，
版本日志以前都写在各自的代码里（`src/config/changelog.ts` / `lib/config/changelog.dart`），
改一边另一边不跟着变。真实发生过：接上云端之前，App 还停在 `1.30.6`，网页版已经到 `1.30.8`——
用户看到的就是「一个网页版一个 Flutter 的日志不同步」。

## 现在的口径

| 角色 | 在哪 | 说明 |
|------|------|------|
| **真源** | D1 `changelog` 表 | 两端都从 `GET /api/changelog` 读它 |
| **编辑入口** | `src/config/changelog.ts` | 只在这一个文件里加/改日志，再用脚本推上库 |
| **播种 + 兜底** | 同上 + 生成到 App 的 `lib/config/changelog.dart` | 接口不可用（表没迁移 / 还没同步 / 断网）时，两端各自退回自己 bundle 里这份 |

数据流：

```
src/config/changelog.ts ──(npm run changelog:sync)──▶ D1 changelog ──GET /api/changelog──┬─▶ 网页版设置页
                        └─(npm run changelog:fallback)─▶ SekaiNook-App/lib/config/changelog.dart
                                                                                        └─▶ App 设置页（读不到云端时用它兜底）
```

## 表结构（`migrations/0006_changelog.sql`）

| 列 | 说明 |
|----|------|
| `version` | 主键，例如 `1.31.0`。重复同步天然是覆盖，不会攒出重复行 |
| `date` | 展示用的时间串 `YYYY-MM-DD HH:mm:ss`，原样透出，不做时区换算 |
| `title` | 这一版的一句话主题 |
| `changes` | 改动条目，**JSON 数组字符串**（SQLite 没有数组类型） |
| `sort_order` | 「代码数组里的下标」，0 = 最新。**顺序的唯一真源是数组顺序**，不靠 version / date 排序 |
| `updated_at` | 同步写入时间 |

排序为什么不用 `version` 或 `date`：版本号是字符串，`'1.9.0'` 会排到 `'1.10.0'` 后面；
`date` 也可能同一天里连着写好几条。数组下标最诚实。

## 接口

`GET /api/changelog`（无鉴权，只读，路由文件 `functions/api/changelog/index.ts`，读取逻辑 `functions/_lib/changelog.ts`）

```json
{
  "version": "1.31.0",
  "entries": [{ "version": "1.31.0", "date": "2026-10-17 22:40:00", "title": "…", "changes": ["…"] }],
  "ready": true
}
```

- **永远回 200**，用 `ready` 表达「这份数据能不能用」：`ready:false` = 表没迁移 / 还没播种，
  客户端据此退回自己 bundle 里那份。这样两端都只需要一个分支，不必处理 4xx/5xx。
- 只读、不提供写接口：内容的唯一入口是仓库里的 `src/config/changelog.ts`，
  写接口会绕开 review 且仓库铁律是不引入鉴权中间件。

## 日常操作：加一条版本日志

1. 改 `src/config/changelog.ts`：`APP_VERSION` 升到新版本号，在 `CHANGELOG` **最前面**加一条
   （`version` / `date` / `title` / `changes[]`）。
   **`date` 必须写真实时间** —— 项目历史上因日期乱写（甚至写成未来）被要求订正过一次（提交 `197033f`）。
2. `npm run changelog:sync`：把内容推到线上 D1（没部署权限时先 `--dry` 生成 SQL，见下）。
3. `npm run changelog:fallback`：把同一份内容生成到 App 仓库的 `lib/config/changelog.dart`。
4. 两端各自提交。网页版部署即可看到新日志；App 下次发版会带上新的兜底（就算不发版，
   只要云端同步过了，打开 App 也是新的）。

> 脚本会先自检：版本号重复、`date` 格式不对、`changes` 为空、`APP_VERSION` 与最新一条不一致，
> 都会直接报错退出 —— 这些错同步出去以后查起来很麻烦。

## 命令与环境变量

| 命令 | 作用 |
|------|------|
| `npm run changelog:sync` | 生成 SQL 并推到**线上** D1 |
| `npm run changelog:sync:local` | 同上，推**本地** D1（`npm run dev:api` 时用） |
| `npm run changelog:sync -- --dry` | 只生成 SQL + 打印命令，不写库 |
| `npm run changelog:fallback` | 生成 App 仓库里的兜底文件 |
| `npm run changelog:fallback:check` | 只检查兜底文件是否与网页版一致（漂移则退出码 1） |

环境变量：`SEKAINOOK_DB`（D1 库名，默认 `sekainook`）、`SEKAINOOK_APP`（App 仓库路径，默认 `../SekaiNook-App`）。

生成的 SQL 落在 `migrations/.changelog-sync.sql`（已 gitignore）。wrangler 跑不动时可以手动执行：

```bash
npx wrangler d1 execute sekainook --remote --file=migrations/.changelog-sync.sql
```

为什么脚本是「UPSERT + 删多余」而不是「先清空再灌」：两条语句之间有个空窗，正好有人打开设置页
就会看到空日志；而且万一第二条失败，库里还是完整的旧数据而不是空的。

## 部署顺序

```bash
npm run db:migrate:remote     # 1. 先建表（0006）
npm run changelog:sync        # 2. 再灌内容（只建表不灌，两端会退回兜底，页面不会崩但日志停在旧版本）
npm run deploy                # 3. 最后部署前端
```

## 怎么知道出问题了

- **设置页**：版本日志卡底部那行小字会写「已与云端同步」或「暂时读不到云端，显示的是本机内置的那一份」。
- **全站自检**（管理员 → 全站自检）：`env.changelog`「版本日志已上云」会查条数、顺序、最新版本、
  字段完整性、版本号是否重复。**这条检查专治「迁移跑了但忘了同步内容」**——那种情况下接口老实回
  `ready:false`，两端安静地退回兜底，页面一片祥和，只有日志停在旧版本。
- 自检清单版本已从 1 升到 2（多了这一条），`env.tables` 期望张数从 6 变 7（多了 `changelog`）。
